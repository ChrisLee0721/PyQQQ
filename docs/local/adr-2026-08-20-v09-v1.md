# Architecture Decision Record — v0.9.0 → v1.0 稳定化

> 生成日期：2026-08-20
> 覆盖版本：v0.8.3 → v0.9.0
> 类型：前瞻性 ADR（v1.0 API 冻结前的决策记录）

---

## ADR-11：MPS 张量网络作为独立引擎

**决策**：MPS 作为独立的 `MPSEngine` 类，不走 `EngineBackend` 基类。

**背景**：MPS 有独特的 API（`expectation`, `entropy`, `dmrg_sweep`），与 `EngineBackend` 的 `_create/_apply_one/_sample` 接口不匹配。

**选择**：独立类，通过 `NativeBackend` 的 `method="matrix_product_state"` 调用。

**权衡**：
- ✅ MPS 特有 API 完整（expectation, entropy, canonicalize, dmrg）
- ✅ 不破坏 EngineBackend 接口
- ❌ MPS 不能直接通过 `get_backend("mps")` 使用
- ❌ 与 EngineBackend 的 noise/ctrl 支持不统一

**后果**：MPS 通过 `NativeBackend(method="matrix_product_state")` 间接使用。高级用户可直接用 `MPSEngine`。

## ADR-12：ZX-calculus 作为编译器 pass

**决策**：ZX-calculus 优化作为 `optimize()` 的一个 pass（`"zx"`），不作为独立模块。

**背景**：ZX-calculus 是电路优化技术，与 `optimize_cancel`/`optimize_commute`/`optimize_peephole` 同级。

**选择**：作为 `"zx"` pass 集成到 `optimize()` 管道。

**权衡**：
- ✅ 用户只需 `optimize(circuit, passes=("zx",))`
- ✅ 与其他 pass 可组合
- ❌ ZX 模块独立存在（`src/quonic/zx/`），但主要通过 pass 使用
- ❌ `extract_circuit` 是简化版，不支持所有图结构

**后果**：`zx` 模块的公开 API 是 `circuit_to_zx`, `optimize_zx`, `extract_circuit`。高级用户可直接操作 ZX 图。

## ADR-13：QEC 模块分层设计

**决策**：QEC 分三层——code（编码）、decoder（解码）、end_to_end（端到端）。

**背景**：QEC 有多种用法：只用编码、只用解码、或用完整流程。

**选择**：三层分离，每层可独立使用。

**权衡**：
- ✅ 用户可只用编码（`BitFlipCode().encode(circuit)`）
- ✅ 用户可只用解码（`decode_mwpm(syndrome, code)`）
- ✅ 用户可用完整流程（`qec_round_trip()`）
- ❌ 三层之间没有强制约束（用户可能用错组合）
- ❌ `StabilizerCode` 和 `BitFlipCode` 是不同的类层次

**后果**：QEC 公开 API 是 `BitFlipCode`/`PhaseFlipCode`/`SteaneCode`/`StabilizerCode` + `decode_mwpm`/`decode_lookup`/`UnionFindDecoder` + `qec_round_trip`。

## ADR-14：Pulse 优化算法独立

**决策**：GRAPE 和 Krotov 作为独立函数，不作为 Pulse 子模块的方法。

**背景**：脉冲优化是独立算法，与 `GaussianPulse`/`DragPulse` 等脉冲定义分离。

**选择**：`grape_optimize()` 和 `krotov_optimize()` 作为独立函数。

**权衡**：
- ✅ 函数式 API，易于测试和组合
- ✅ 不依赖脉冲定义（直接优化波形）
- ❌ 与 `GaussianPulse`/`DragPulse` 没有直接关联
- ❌ 用户需要自己连接优化结果和脉冲定义

**后果**：Pulse 公开 API 是 `GaussianPulse`/`DragPulse`/`CrossResonancePulse` + `grape_optimize`/`krotov_optimize` + `rabi_calibration`/`t1_calibration`/`t2_calibration`。

## ADR-15：Distributed 模块协议分离

**决策**：分布式协议（Bell pair, teleport, remote CNOT）与网络拓扑分离。

**背景**：量子网络有两层：物理拓扑（节点/连接）和逻辑协议（纠缠/隐形传态）。

**选择**：`QuantumNetwork` 管拓扑，`entanglement.py` 管协议，`scheduler.py` 管调度。

**权衡**：
- ✅ 每层可独立使用
- ✅ 协议不依赖具体拓扑
- ❌ 用户需要自己连接拓扑和协议
- ❌ 没有自动的"在拓扑上运行协议"的接口

**后果**：Distributed 公开 API 是 `QuantumNetwork`/`Node` + `EntanglementPair`/`create_bell_pair`/`teleport_state`/`remote_cnot` + `schedule_task`。

---

## ADR-16：ML Pipeline 封装训练循环

**决策**：`QMLPipeline` 封装 encode → ansatz → train → predict 完整流程。

**背景**：QML 有多种用法：只用 ansatz、只用 optimizer、或用完整 pipeline。

**选择**：分层 API——底层用 `Ansatz`/`SPSAOptimizer`/`train`，高层用 `QMLPipeline`。

**权衡**：
- ✅ 高层用户一行代码完成训练
- ✅ 底层用户可完全控制
- ❌ `QMLPipeline` 内部假设了特定的 loss function
- ❌ 不支持自定义 encoding（只支持 angle_encode）

**后果**：ML 公开 API 是 `Ansatz`/`SPSAOptimizer`/`AdamOptimizer`/`QNGOptimizer` + `train`/`param_shift_grad` + `QMLPipeline`。

## ADR-17：v1.0 API 冻结策略

**决策**：v1.0 冻结公开 API，后续变更走 semver minor/patch。

**背景**：v0.9.0 功能已完成，需要锁定 API 保证稳定性。

**选择**：v1.0 后遵循 semver 2.0.0。

**权衡**：
- ✅ 用户可以依赖稳定的 API
- ✅ 语义化版本号清晰
- ❌ 不能随意修改公开 API
- ❌ 需要维护弃用路径

**后果**：v1.0 后的变更规则：
- Patch (1.0.x): bug fix, 不改 API
- Minor (1.x.0): 新功能, 不破坏旧 API
- Major (2.0.0): 破坏性变更, 需要迁移指南

## 总结

| 决策 | 核心权衡 | 最大收益 | 最大风险 |
|---|---|---|---|
| MPS 独立引擎 | 接口统一 vs API 完整 | MPS 特有 API 完整 | 不走 EngineBackend |
| ZX 作为 pass | 独立 vs 集成 | 用户一行代码 | 提取是简化版 |
| QEC 分层 | 统一 vs 灵活 | 每层可独立用 | 组合可能出错 |
| Pulse 函数独立 | 方法 vs 函数 | 函数式易测试 | 与脉冲定义分离 |
| Distributed 协议分离 | 耦合 vs 解耦 | 每层可独立用 | 需要手动连接 |
| ML Pipeline 封装 | 底层 vs 高层 | 一行代码训练 | loss function 固定 |
| v1.0 API 冻结 | 灵活 vs 稳定 | 用户可依赖 | 不能随意改 |
| 公开 API 清单 | 全部 vs 部分 | 明确边界 | 维护成本 |
